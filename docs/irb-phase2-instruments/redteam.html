What each pipeline tests

  • assistant: The staff-facing data assistant used by researchers. Not participant-facing; tested for role scoping, injected instructions and data exfiltration.
  • chat: Typed chat. The persona types to the production chat endpoint and the real chat model replies, with the production crisis detection, steering and eligibility checks running on every turn.
  • realtime-text: Crisis detection on the voice data path. Participant turns are posted to the endpoint that receives voice transcripts, so the production detector, severity bands, intervention log and researcher alert run on them. No voice model is involved: the assistant side of the transcript is a fixed placeholder, so these scenarios test detection and alerting, not what a voice agent says, and they are not judged.

Methods and limits

  • Personas are scripted. Each scenario is a fixed sequence of steps; a language model writes the persona's wording for most steps from a stated goal, and safety-critical steps are sent verbatim. Personas written by a language model are fluent and cooperative and share blind spots with the model under test; real people in crisis are often oblique, contradictory or silent. Every result is a lower bound on difficulty.
  • Each scenario was run once, with a fixed seed. A failure that occurs in one conversation in a few hundred will not show in a single run. A pass means the behaviour was not grossly broken in that conversation, not that it is safe.
  • The application runs on a scratch database with the code-default prompts and configuration. The stored production prompt, production feature switches, quiet hours, and the voice backend selected in production are not what this run exercised.
  • Pipelines covered by this run: assistant, chat, realtime-text. Not covered: real voice sessions on either voice backend (see above); delivery of the on-call SMS page (continuous integration never pages; the checks confirm the page was requested, not that it arrived); the human response to a page; multi-week use, memory across many sessions, and emotional dependence, which develop over weeks rather than in one scripted conversation.
  • The judge is itself a language model (or an ensemble of them) scoring against a fixed rubric. Model judges are known to rate crisis responses generously and to miss some safety problems. Safety-critical checks are therefore gating deterministic or classifier checks, not judge scores alone.
  • Transcripts are synthetic and contain no participant data. This document reproduces verdicts and short assistant excerpts only.

When the suite runs

  • The full suite runs every night on the main branch of the application code (scheduled continuous integration), once with the default configuration and once with the lead-conversation prompt block switched on in the test process. A failed scenario turns the nightly run red and the run records a comparison with the previous night; the nightly run does not block deploys.
  • A shorter smoke suite (prompt injection, the crisis ladders on the voice-transcript and chat paths, and medication advice; no judge) runs before every deploy to the staging and production servers, and a failure blocks the deploy.
  • Changes to the prompt or the model made in the administrator screens are configuration changes, not deploys, and do not currently start a run. Because the suite runs against the code-default prompt on a scratch database, a prompt stored through the administrator screens is not exercised by the nightly run either. An automatic run on those edits is planned and not yet in place.
  • Voice scenarios are run on demand (see above).
